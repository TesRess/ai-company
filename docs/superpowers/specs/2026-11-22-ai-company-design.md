# AIカンパニー 設計書

作成日: 2026-11-22

## 1. 目的と背景

社長・企画・エンジニア・レビューの役割を持つAIエージェントのチームが、オーナー（利用者本人）の代わりに**小さなアプリやWebサービスを作る**仕組みを作る。

目的は**オーナー自身の仕事や生活の困りごとを解決すること**。収入を得ることや、仕組みづくりそのものは目的ではない。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**
- オーナーが `/company` と話しかけるだけで、社長役が聞き取りを始め、アイデアの提案から実装・レビューまでチームで進む。
- 社長役がオーナーの困りごとから作るものの候補を出し、オーナーが選ぶ。
- エンジニア役が作ったものは、オーナーが確認してから取り込む。

**非ゴール（今回はやらない）**
- オーナーが見ていない間に自動で動き続けること（クラウドでの並行実行や定期実行は後で検討する）。
- 営業・マーケティング役。
- 専用の管理画面や独立したプログラム。

**アンチゴール（動いても失敗とみなすもの）**
- AIがオーナーの確認なしに、公開・リリース・課金・外部への送信をすること。
- AIがオーナーのメール・カレンダー・Notionなどの個人データを読むこと。
- 役割どうしのやり取りばかり増えて、実際に使えるものができないこと。
- 大きすぎて使い始めるまで何週間もかかるものを作ること。

## 3. 制約

- **Claude Code の上で動かす**。追加のAPI費用やサーバーは使わない。
- 困りごとは**オーナーへの聞き取りだけ**で集める（個人データは読まない）。
- 最終確認は必ずオーナーが行う。
- GitHubリポジトリ `ai-company` に置く。作成はオーナーがGitHub上で行う（このセッションからはリポジトリを作れないため）。それまではローカルで作成する。

## 4. 検討した作り方

| 案 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| **1. Claude Code のサブエージェント（採用）** | リポジトリに4役の設定とコマンドを置く | 追加費用なし、1日程度で作れる、変更はプルリクエストで確認できる | オーナーが話しかけている間しか動かない |
| 2. Claude Agent SDK で専用プログラム | 独立したプログラムと管理画面 | 自由に作り込める | API費用、数週間の開発、保守が必要。仕組みづくり自体が目的化する |
| 3. クラウドで複数セッション並行 | 社長セッションが他の役のセッションを起動 | 不在中も進む | 複雑で追いにくい。最初の一歩には大きすぎる |

オーナーは**案1**を選んだ。理由: 目的は困りごと解決なので、早く動かして使ってみるのが近道。必要になったら案3を後から足せる。

## 5. オーナーが決めたこと

- 役割はチーム制で、アプリ・Webサービスを作る仕事を任せる。
- 社長役に**アイデア出しから**任せる。ただし作るものを最終的に選ぶのはオーナー。
- 困りごとは**聞き取り方式**で集める。
- 最終確認はオーナー自身が行う。
- 作り方は案1（Claude Code のサブエージェント）。

## 6. 設計

### 6.1 役割（4役）

| 役 | 仕事 | やらないこと |
|---|---|---|
| **社長（CEO）** | オーナーに聞き取りをして困りごとを集める。解決するアイデアを2〜3案出し、評価して提案する。選ばれた案の仕事を割り振り、進行を管理し、オーナーに報告する | コードを書かない。オーナーの選択なしに作り始めない |
| **企画（PM）** | 選ばれたアイデアを、小さな仕様（誰が・何を・どこまで作るか、完成の条件）にまとめる | 仕様を膨らませない（1〜2週間で使い始められる大きさに収める） |
| **エンジニア** | 仕様に沿ってコードを書き、テストし、動くことを確かめる | 公開・デプロイ・課金・外部送信をしない |
| **レビュー** | できたものを仕様と照らしてチェックし、問題点をエンジニアに戻す。問題がなければオーナー向けの報告をまとめる | 自分でコードを直さない |

### 6.2 アイデアの評価基準（社長役）

1. オーナーが毎日または毎週使うか
2. 困りごとがどれだけ減るか（時間・手間・ストレス）
3. 小さく早く作れるか（1〜2週間で使い始められるか）

### 6.3 仕事の流れ

```
オーナー: /company
  └ 社長: 聞き取り（困りごとを質問する）
  └ 社長: アイデア2〜3案を評価つきで提案
オーナー: 1案を選ぶ  ← 確認ポイント①
  └ 企画: 仕様を書く
オーナー: 仕様を確認  ← 確認ポイント②
  └ エンジニア: 実装・テスト
  └ レビュー: チェック（問題があればエンジニアに戻す）
  └ 社長: 結果をオーナーに報告
オーナー: 確認して取り込む ← 確認ポイント③
```

確認ポイントでは、AIは必ず止まってオーナーの返事を待つ。

### 6.4 記録

会社の状態は、リポジトリ内のファイルに残す。次に `/company` を呼んだとき、社長役はこれを読んで続きから始める。

- 聞き取った困りごとの一覧
- 提案したアイデアと、オーナーが選んだもの・選ばなかったもの
- 各プロダクトの仕様と進み具合

### 6.5 置き場所

- 4役の設定: Claude Code のサブエージェント定義（`.claude/agents/`）
- 呼び出しコマンド: `/company`（`.claude/commands/` またはスキル）
- 作るプロダクト: 同じリポジトリ内のフォルダ（例: `products/<名前>/`）
- 会社の記録: 同じリポジトリ内のフォルダ（例: `company/`）

### 6.6 オーナーが決めた、プロダクトの範囲

- **プロダクトはオーナーのパソコンだけで使う**。Webへの公開やスマホ対応はしない。社長役は「パソコン上で動くツール（ブラウザで開くローカルのツール、スクリプトなど）」として作れるアイデアだけを出す。
- **完成したプロダクトは、オーナーのメールなどの個人データを扱ってよい**（オーナーが自分で動かすとき）。ただし一般公開はしない。
- AIが作業中にオーナーの個人データを読まない、というルールは変わらない。エンジニア役とレビュー役は、開発とテストに**ダミーデータ**を使う（設計者の判断）。

### 6.7 決めごと（設計者の判断。オーナーは確認して直せる）

- **「外部送信」の意味**: オーナーに代わって人やサービスに何かを送ること（メール送信、SNS投稿、フォーム送信、公開など）。パッケージのインストール（`npm install` など）や、社長・企画役のWeb調査は含まない。
- **同時に進めるプロダクトは1つだけ**。`/company` を再度呼ぶと、進行中のプロダクトがあればその続きから始める。新しく始めるのは、オーナーが完了または中止を決めてから。
- **確認ポイント③の取り込み方**: エンジニア役はプロダクトごとの作業ブランチにコミットする。GitHubリポジトリができたら、プルリクエストを作り、オーナーがマージする。AIはメインブランチに直接コミットせず、マージもしない。例外として、社長役は `company/` の記録だけをメインブランチに直接コミットする（記録がクラウドの作業環境ごと消えないようにするため。実装時の判断）。

## 7. 作る人に任せること

- 各役のプロンプトの具体的な文面
- 記録ファイルの形式と細かい配置
- プロダクトごとの言語・フレームワークの選び方（エンジニア役が仕様に合わせて選ぶ）
- 各役が使えるツールの範囲（ただしアンチゴールを守ること）
